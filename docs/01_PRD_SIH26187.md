## Section 1: Problem Statement & Strategic Context

### 1.1 Core Constraint (Verbatim Intent)

A software-only platform that transforms existing IP CCTV into intelligent surveillance — explicitly without requiring dedicated FRS, ANPR, or smart-camera hardware. Must work on whatever IP CCTV is already installed.

### 1.2 Why This Approach (Strategic Framing for Pitch)

The Ministry of Home Affairs has already tried the hardware-heavy route twice, and both failed — this is the entire reason the PS demands software-only.

- **BOLD-QIT (India-Bangladesh riverine border, Assam):** Rs.86 crore spent, equipment unused/junked, sub-standard gear, network collapsed.
    
- **CIBMS Confirmed failure causes (from IDSA research):**
    
    1. Sensor-fusion software integration was the real bottleneck, not hardware deployment.
        
    2. False-alarm epidemic from wildlife/weather/vegetation triggering constant alerts.
        
    3. Operator competence gap — jawans lacked technical expertise to run sophisticated equipment.
        
    4. Maintenance collapse — high electronics cost, no spare parts, weather degradation.
        
    5. Vague procurement requirements led to over-engineering.
        

**Positioning Statement:** Do not sell MHA new hardware boxes — give them software that makes existing cameras smart, survives remote conditions, and is operable by non-technical jawans. Every PRD feature below should trace back to one of the four CIBMS failure modes it fixes, because that traceability is the pitch's credibility.

### 1.3 Target Users

- **Primary:** SSB/BSF/ITBP/Assam Rifles jawans at Border Outposts (BOPs) — low computer literacy baseline, confirmed via UK-funded digital literacy program for Joint Border Task Force personnel.
    
- **Secondary:** Command centre operators at Sector HQ — slightly more technical but still require extremely simple dashboards.
    
- **Tertiary:** System administrators at Force HQ — backend config, profile updates, model version management.
    

## Section 2: Core Product Definition

### 2.1 What This System Is

A software-only AI analytics layer that sits on top of existing IP CCTV infrastructure. It ingests multiple RTSP/ONVIF camera feeds, runs lightweight AI models locally at the edge, normalizes all detections into a unified event schema, publishes events over a single validated bus, and presents a human-operated command dashboard with real-time alerts and forensic logging.

### 2.2 What This System Is NOT

It is NOT a hardware replacement for cameras. It is NOT a dedicated FRS box. It is NOT an ANPR camera. It is NOT a thermal imager. It is NOT a one-giant-model black box. It does NOT extend physical IR camera range — it improves what the sensor already captures. It does NOT perform long-range face identification — physics limits resolution, not fixable by better AI.

### 2.3 The Five-Model Architecture (Locked Claim)

Model A (1 lightweight filter/classifier) + Model B's four engines (Face, ANPR, Posture, Trajectory) = 5 models by design. Explicitly NOT one giant model — this is a stated architectural strength, not a limitation.

- **Caveat for the Pitch:** The "5 lightweight models running in parallel" claim is UNVERIFIED until benchmarked on actual target hardware (Jetson Orin Nano class). Do not present as confirmed efficiency without testing. Enforce that discipline into the PRD acceptance criteria, not just as a footnote.
    

## Section 3: Capability Requirements & Architecture Coverage

**1. Human Detection and Tracking**

- **Status:** Fully Covered (Model B — Trajectory Engine + Multi-Camera Fusion).
    
- **Requirement:** Detect humans in camera FOV, assign persistent track IDs, maintain identity across frame drops and brief occlusions, fuse tracks across multiple cameras viewing the same entity.
    
- **Success Criteria:** >90% detection rate in daylight, >75% in night/low-light (within sensor limits), <5% ID switch rate across 100-frame sequences, multi-camera fusion prevents same person tracked as two separate entities.
    

**2. Vehicle Detection and Classification**

- **Status:** Covered for motorized; gap for animal carts (Model B — Trajectory Engine). Needs labeled dataset for animal-cart class.
    
- **Requirement:** Detect motorized vehicles (2-wheeler, 4-wheeler, heavy vehicle), classify type, read license plates at chokepoints/ICPs only.
    
- **Success Criteria:** >85% detection rate for motorized vehicles, >80% classification accuracy across 3 classes.
    

**3. Face Detection**

- **Status:** Covered within range limits (Model B — Face Engine). Close Range only.
    
- **Requirement:** Detect and extract faces from close-range cameras (chokepoint/ICP/gate), generate 512-dim embedding vector, match against watchlist.
    
- **Success Criteria:** >90% detection rate at <=10m equivalent range, embedding quality sufficient for 1:N matching at 1:1000 scale. Long-range face ID (>30m) explicitly NOT promised.
    

**4. ANPR (Automatic Number Plate Recognition)**

- **Status:** Partial — chokepoint-only (Model B — ANPR Engine). High-mounted BOP cameras cannot reliably read plates.
    
- **Requirement:** Detect license plates, perform perspective correction where possible, recognize multi-script (Latin + Devanagari + regional) plates, output structured plate text + confidence + image evidence.
    
- **Scope Limitation:** ANPR scope explicitly limited to ICP/chokepoint cameras where vehicles pass at controlled speed/distance.
    
- **Success Criteria:** >80% plate detection at chokepoints, >70% character recognition accuracy on Indian multi-format plates.
    

**5. Virtual Fence Intrusion Detection**

- **Status:** Fully covered — strongest capability (Model A — multi-frame confirmation).
    
- **Requirement:** Two-tier geofence (warning zone + intrusion zone), detect boundary crossing, multi-frame confirmation before flagging, suppress wildlife/weather false triggers.
    
- **Success Criteria:** <2 false alerts per night per camera (directly fixes documented 50 false alerts/night failure), >95% true intrusion detection at fence line, 2-3 frame confirmation latency acceptable (<3s at 1 FPS sampling).
    

**6. Suspicious Activity Detection**

- **Status:** Core covered; context layer NOT built (Model B — Posture Engine + Border Context Profile).
    
- **Requirement:** Detect postures and movements indicative of suspicious behavior — crawling, crouching, running, carrying large objects, loitering.
    
- **Success Criteria:** Posture Engine achieves >75% accuracy on 6 defined posture classes. Full suspicious activity detection requires Border Context Profile (time+zone+pattern weighting) — biggest unbuilt dependency. Without context: same crawling at 2am near fence = flag, same crawling at 6am on farm path = ignore.
    

**7. Night-Time Movement Detection**

- **Status:** Covered within sensor limits (Model A pre-processing).
    
- **Requirement:** Enhance low-light footage via preprocessing, detect movement in IR-illuminated scenes, maintain detection pipeline at night without separate night-only model.
    
- **Success Criteria:** Cannot extend physical IR camera range — software improves what's captured, not hardware reach. Zero-DCE preprocessing + YOLO maintains >60% detection rate in typical BOP IR footage.
    

**8. Real-Time Alerts and Event Logging**

- **Status:** Fully covered (Event bus + Orchestrator). Engineered against 50 false alerts/night failure mode.
    
- **Requirement:** Generate alerts within 5 seconds of trigger confirmation, log every event with timestamp + camera ID + evidence hash + model version, support forensic query by time/zone/camera/entity type, export evidence package for legal proceedings.
    
- **Success Criteria:** End-to-end latency (trigger → alert on dashboard) <5s for critical events, <10s for standard events. Event log immutable and tamper-evident.
    

## Section 4: User Stories

**As a jawan/BOP operator:**

- I want the dashboard to show me one clear alert with a confidence tag, not a wall of raw detections, so I don't get alert fatigue (the exact failure that killed CIBMS).
    
- I want a fallback view that still shows something if a specialized engine goes down, so I'm never blind.
    

**As a command centre supervisor:**

- I want every event tagged with camera ID, zone, timestamp, and evidence reference so I can audit any alert after the fact.
    
- I want engine health and pipeline-flow status visible at all times (right panel), so I know when I'm looking at degraded data vs. full-confidence data.
    

**As a judge (internal SIH round):**

- I want to see a live or staged demo proving the system can suppress false triggers across 2–3 frames — this is the single most differentiating, most defensible claim in the whole project.
    
- I want honest scoping — the team should say "ANPR only works at chokepoints" rather than overclaim, because judges probing this exact PS will ask.
    

## Section 5: Non-Functional Requirements

### 5.1 Performance

- Edge inference latency per frame <200ms on target hardware.
    
- System throughput: minimum 4 camera feeds processed simultaneously per edge node.
    
- Dashboard refresh rate: 1-2 FPS live view, event list updates in real-time.
    

### 5.2 Reliability

- **Fallback logic:** If any Model B engine fails, that camera's traffic routes back through Model A's basic motion+trigger detection — safety floor prevents total blindness.
    
- **Camera Health Monitor:** Detects lens obstruction, darkness, frozen stream, FPS anomalies.
    
- System must operate 24/7 with <1 hour unplanned downtime per week.
    

### 5.3 Operability (Non-Technical Jawan Constraint)

- Dashboard UI must be operable by personnel with minimal computer literacy — large buttons, clear color coding (red=critical, yellow=warning, green=normal), minimal text, icon-driven controls.
    
- No command-line interaction required for normal operations.
    
- Alert acknowledgment requires single click.
    
- Jawan training time to independent operation target: <30 minutes.
    

### 5.4 Scalability

- Architecture must scale from single BOP (4 cameras) to Sector HQ (50+ cameras) to Force-level (1000+ cameras) without architectural redesign.
    
- Event bus (MQTT → Kafka migration path) supports horizontal scaling.
    
- Model A is lightweight enough to run one instance per camera; Model B engines can be shared across cameras or run per-camera based on load.
    

### 5.5 Security

- No separate/bypass bus line for triggers — all traffic through one validated bus, severity-tagged.
    
- **Anti-spoofing:** Footage lacking trajectory/posture/temporal continuity gets flagged as possibly injected/replayed.
    
- **Evidence integrity:** Every event carries SHA-256 hash + model version + timestamp.
